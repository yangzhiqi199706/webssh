故障接管功能说明

触发条件：本机角色 备机 + 主备总开关启用 + 缓冲启用。
监测过程：
  1. 每 3 秒探测主机 SSH/DB 端口
  2. 按「失联判定」规则连续失败达到「连续失败次数」 → 进入倒计时
  3. 倒计时期间主机心跳恢复 → 立即重置回监测态
  4. 倒计时归零 → 触发接管动作
接管动作（5 步）：
  1. SSH 二次握手主机（脑裂防护）：再尝试 SSH 一次主机；如果意外能握手成功，说明只是网络分区，取消接管
  2. 检查本机 dcim 容器存在
  3. DELETE FROM dcim-alarmlist（清空告警表，避免基于陈旧告警重复推送/误处理）
  4. UPDATE dcim-device SET status=1
  5. docker exec dcim systemctl restart dcim
已接管后：
  • 持续监测主机端口，但不再重启 dcim（首次成功后业务已在备机跑）
  • 主机被动逻辑触发：主机 5s 内自动 docker exec dcim systemctl stop dcim 让位
  • 主机端「数据库同步」按钮被锁定，避免数据撕裂
  • UI 顶部出现「接管中」红色徽章
★ 自动让位（核心防撕裂机制）：
主机重启时，OS/SSH（约 20s）比 dcim.service 自启（约 40s）早 20 秒上线。备机在已接管态下，连续 N 次心跳（默认 5 次 = 15 秒）探到主机 SSH 或 DB 端口任一通，就立刻自动让位：
  1. UPDATE dcim-device SET status=-1
  2. docker exec dcim systemctl stop dcim
  3. 主机 5s 内 peer watch 感知 → systemctl start dcim 接回业务
时序保证 0 撕裂：备机让位完成（T+15s）< 主机 dcim 自启（T+40s），中间还有 ~20 秒安全窗口。
让位后进入冷却期（默认 60 秒，可在表单里调整），期间不再触发任何接管/让位，避免主机时通时断震荡。
手动「重置接管状态」（运维主动让位，业务回切到主机）：
  1. 动作与「自动让位」完全一致：UPDATE status=-1 + stop dcim
  2. 主机 5s 内自动 start dcim 接回
  3. 同样进入冷却期（按表单配置的秒数，默认 60s）
⚠ 重要：建议在配置完成后先点「测试接管命令」做一次 dry-run，确认 docker / mysql 权限正常，避免真正失联时才发现命令跑不通。

cron 语法说明（5 字段）

*  *  *  *  *
分 时 日 月 周（0-6 周日=0）
支持的语法：
  • *    该字段任意值
  • 5    精确到 5
  • 1,3,5    列表
  • 9-17    范围
  • */15    步长（每 15 单位一次）
常用例子：
  • 0 3 * * *   每天 03:00
  • 0 */6 * * *   每 6 小时一次（00/06/12/18 整点）
  • 0 2 * * 0   每周日 02:00
  • 30 1 1 * *   每月 1 号 01:30
  • */5 * * * *   每 5 分钟一次（仅测试用，业务不要开）
注意：调度精度为分钟级，不支持秒。本面板配置不支持 @reboot / @daily 等扩展语法。

数据库同步注意事项

1.
收尾检查（重要）：当项目完成到双机热备阶段时，请检查数据库 dcim-device 表中的 status 字段是否全部为 1， 一定要删除 status 为 -1 的条目，不然会出现数据混乱的问题。
2.
备机现象解释：数据库同步后备机的「设备管理」为空是正常情况。这里做了 假删除（status=-1），目的是 防止备机自动重启后与主机争抢数据。
参考：同步流程会先把主库数据完整覆盖到备机，再把 dcim-device.status 统一改成 -1。备机当前的 dcim 库备份在 /opt/webssh/logs/ha-sync-bak-<时间戳>.sql.gz。
