# 2026-09-17 串口扫描卡死排查

## 现场与证据

用户确认 11:08—11:10 操作串口调试的端口扫描时网页无响应，执行 `systemctl restart webssh webssh-protocol` 后恢复。用户进一步确认故障不在 192.168.50.61，当前无法连接生产环境，未进行远端检查。

用户提供的 logs.rar 中，sms-scheduled.log 从 10:49:53 至 11:07:53 每分钟记录一次；11:08—11:09 记录中断，11:10:12 重新初始化，11:11:12 起恢复。记录缺口支持主进程停顿或停止的可能，但不能单独区分阻塞、退出、OOM 或其他系统异常。

上述日志来自原任务已解压保存的归档。当前桌面同名 logs.rar 已变为 603 字节，仅包含 docker-restart.log、docker-scheduled-restart.log 和 firewall.log。新归档同样记录 11:10:12 初始化；两项 Docker 重启功能均为 enabled=false，没有故障窗口内自动重启 Docker 的记录。

## 代码检查

- 前端扫描按钮请求 `/api/serial/ports?probe=1`，没有请求超时；请求不结束时按钮保持“扫描中”。
- 后端在 Node 主线程同步枚举 `/dev`、读取 `/proc/tty/driver/serial`，并逐个 `fs.openSync` / `fs.closeSync` 探测设备。
- `O_NONBLOCK` 不保证所有驱动的 open/close 和 proc 读取都立即返回。一旦同步系统调用停顿，HTTP、WebSocket 和定时回调都无法继续处理。
- `uart:unknown` 判断位于设备打开之后，因此已知无物理 UART 的端口仍会被探测。
- 已被本进程 serialLocks 登记占用的端口会跳过，但这不代表识别了其他程序占用的设备。

## 本地机制验证

用 Node vm 加载 server.js 的实际扫描路由，模拟一个 uart:unknown 的 ttyS0，并仅在模拟 openSync 中注入 600 毫秒延迟，不启动生产服务、不访问真实设备。

结果：20 毫秒定时器在 611 毫秒才触发；unknown 端口确实被调用 open，然后才返回 uart unknown。

这是同步驱动调用阻塞事件循环的机制验证，不是对生产硬件故障的复现，也未确定真实卡住的是 proc 读取、open 还是 close。

## 结论与后续

当前首要怀疑是扫描路径中的同步设备/驱动调用阻塞 Node 主线程，符合操作触发、全站无响应及定时日志中断的表现。尚不能认定最终根因。

确认实际故障主机后，应只读核查故障窗口的 webssh.out.log、webssh.err.log、systemd 日志和内核日志，确认是否有 OOM、退出记录或串口驱动异常，并核对现场代码版本。

建议修复方向：把包含 proc 读取、设备打开与关闭的扫描放入独立子进程；主进程设置总超时、限制扫描并发，避免异常驱动拖住 Web 服务；提前跳过 unknown UART；前端增加超时反馈。子进程若陷入不可中断内核等待，可能无法立即杀死，因此仍需限制残留任务，不能仅无限重试。

本次仅诊断，未修改业务代码、未部署或重启服务器。
